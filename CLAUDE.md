# Stepwise

Offline Rust TUI for Python evaluation, propositional truth evaluation, and classical natural deduction.

- Use tabs and explicit types. Keep the teaching rules separate from terminal rendering.
- `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked` are the native gates.
- Run `cargo test --locked --test python_oracle -- --ignored --nocapture` when changing Python semantics, and `cargo test --locked --test terminal -- --ignored --nocapture` when changing the terminal adapter. Both are opted into because they need CPython and a pty; Python is a development oracle and a test driver, never a runtime dependency.
- Evidence is a test, not a committed transcript. Anything `STATUS.md` claims must point at something runnable.
- `src/core`: the language-neutral teaching machinery — stable tree IDs, substitution and source mapping, which steps are selectable, typed answer validation, feedback, history and replay. It reaches a language only through `Language` and the closed `Op` pair, and `src/core/language.rs` is the only file in core that names a language module — `rg 'crate::(python|logic)' src/core/` should report no other. Each language owns its own session constructor; no operator rule, precedence number or per-operator explanation lives in core. Core words only what it judged — an attempt, or the next step a hint names; those sentences predate the split, are shared by both languages, and stay byte-identical rather than being reworded per language. It words nothing about the practice around a step, so `Session::hint` returns `None` where no step is left instead of naming a key.
- `src/python`: Python parsing, operator rules, numeric and type semantics, precedence, short-circuit operand rules, every Python explanation, and the Python question grammar.
- `src/logic`: shared symbol aliases, propositional semantics and precedence, bounded BDD equivalence, scoped proof rules, and the propositional question grammar.
- `src/generate`: the shared seed protocol, sampling loop and suitability check; each language module owns its own grammar. Both strategies must complete generated questions with manageable answers. Bump the generation ID version when changing the seed protocol; persisted random questions reconstruct from that ID. Default startup generates a random question or resumes unfinished progress; `n` generates the next question and `p` revisits the current run's history. Samples require `--exercise`.
- `src/exercises.rs`: the question model and the one file format behind it. A question set is a versioned TOML file — `version`, a stable set `name`, title, optional description, and an ordered list of questions that each name their own `kind`: an evaluation question gives source, language and bindings, a proof question gives premises and a conclusion formula. A question's `name` is its identity and the word typed after `--exercise`; it is author-written, so it is a name and not an `id`. The only fields nothing can check are `title` and the optional `note`, and `note` is optional for exactly that reason — a sentence is either true of the question or not, and only a reader can tell. The set compiled into the binary is that one load path's default value, not a second entry: `builtin()` hands `QuestionSet::parse` the embedded `questions/builtin.toml` exactly as a front end hands it a file it read, and `--exercise` resolves against whichever set is loaded. Reading a file belongs to the CLI or the window; the library takes text, checks it and gives back a set, so no path reaches `src/app`. Bindings stay strings of the owning language's source literals — `"0"`, `"0.0"`, `"-0.0"` and `"True"` keep their type and precision — and are never pre-converted to a TOML number or boolean. Every struct denies unknown fields, so a field belonging to the other question type is refused rather than ignored. Bump `FORMAT_VERSION` when the protocol changes; a file naming another version is refused, not guessed at. No JSON question loader remains.
- `src/app`: the front-end-independent application layer — the course of questions and where the next one comes from, the current session with the student's selection, draft and feedback, undo, reset, strategy switching, the archived history, and the progress snapshot. It names no terminal or window library and no file path: `rg 'crossterm|ratatui|PathBuf|std::fs' src/app/` must report nothing. Progress arrives as an explicit snapshot and leaves through `progress()`; deciding when to write it belongs to whoever owns the terminal or the window. Wording runs the other way: a `Report` is a sentence the teaching rules already worded, a sentence a front end handed in through `note`, or a `Notice` — a closed reason with no sentence at all. `Notice` stands beside core's `FeedbackKind` and is never merged into it. Several reasons cannot be said without naming a key or an input device, and the rest keep the same rule rather than splitting the set: `rg 'Enter|Esc|F1|按 [a-z]|点击' src/app/ src/core/` must report nothing. An archived line is the exception and stays here, worded once for every front end — the transcript's taken-back marker and `ProofPractice::appended` are the permanent record, not a live notice. Every match over `Notice` spells its variants out rather than using a wildcard, so a new reason stops compiling until each place has decided what it means. `Course` carries the question-source strategy — random practice, or a fixed set walked in order — so a new source adds a variant rather than a second way to change question. An ordered set ends at its last question instead of generating one. A course holds questions of both kinds: `Lesson` moves through it — forward, back, the end of a set, recording — and the `Task` in hand is an evaluation `Practice` or a `ProofPractice`, so no front end keeps its own way to move between the two, and a set's proofs are never filtered out of its order. Where a course opens is chosen before it is built, by `resume_in_set` and `resume_or_generate`, and an unfinished proof is saved work there like any other. The transcript archives both kinds, so a proof's lines are archived by the same rule for every front end.
- `src/tui`: rendering and input only — an adapter that maps terminal events to app operations and draws app state. It keeps no second copy of the session or the progress, and re-derives no teaching rule: draft ranges, the node under a source byte and which display states to archive all come from `src/app`. It owns every word for every `Notice` — `src/tui/say.rs`, alongside the `?` help in `src/tui/keys.rs` — and its match over `Notice` is exhaustive, so a new reason stops compiling until this front end has said it. Which reports read as good news stays the app layer's rule; `say` asks rather than deciding again. One loop runs the whole lesson and draws whichever view the task in hand needs; in the proof view every letter is proof input, so changing question there takes Ctrl+N / Ctrl+P. Never preselect the correct next node in practice.
- CLI requires exactly one of `--python` / `--logic`; proofs require `--logic`. `--set FILE` imports a question set and replaces the embedded one, turning practice into that file's order; it conflicts with a custom expression, a written-out proof (`--goal`/`--premise`), `--random` and `--equivalent`, and the required language selects inside the set. `--proof NAME` and `--exercise NAME` go through one lookup against whichever set is loaded — `--proof` only insists the question is a proof — so no proof name is hard-coded outside a question set, and `--check-proof` takes its proof from `--proof` or `--goal`. Help/version are exempt. Keep exercise headers to the language/name only; display short-circuit status when toggled rather than in the permanent header.
- Stay inline in the primary terminal buffer; no fullscreen, alternate screen, tree panel or Tab views. Keep the full expression visible above the inline draft and append accepted history to native scrollback.
- Selecting any variable occurrence permits substituting every occurrence of that name in one answer, regardless of precedence. Independent ready operations at equal precedence may be chosen in either order; parentheses have local precedence scopes, not a global depth ranking. Preserve grouping dependencies, operator association and short-circuit guards. This is a priority-based teaching exercise, not strict execution tracing. Clicking a group whose contents are a value removes exactly that pair immediately, without requesting an answer. Record the click as an undoable/replayable action with no input. Preserve syntactically necessary parentheses around a negative power base even after its grouping step.
- Automatically open the answer blank only when the whole expression is a binary operation over two known values. Never auto-submit or auto-solve. Explicit grouping and short-circuit selection remain student actions.
- Exception at completion: when the whole expression is a minus sign over an unsigned numeric value, finish with that signed value without another answer. Do not apply this to inner negations, remaining groups, bool conversion or double negatives. Undo restores the last student step; completion adds no recorded attempt.
- Generate steps, expected values and feedback from the parsed expression, bindings and evaluation rules. Exercises contain source and bindings, never a scripted solution; a proof question gives premises and a conclusion and no step of its derivation. A complete proof lives only in tests — checker fixtures under `tests/fixtures` and test code — never as a sample, in documentation or in anything the program shows: README and the in-app rules explain how to write a line instead, and their examples answer no question. Prose is optional and is never the source of a teaching step. Keep concrete grouping separate from the semantic formulas used by proof checking.
- Short circuit is optional; explain eager Python's teaching behavior in help/feedback without a permanent status heading. Progress must be isolated by teaching-rule version, mode, expression, and typed valuation. Attempts stay keyed by that content, so an edited question starts fresh without losing the old record and a moved file changes nothing; the pointer to the question in hand additionally names its set, so two sets that both hold a question named `q1` never reopen each other's work. A set that fails to load must not touch the progress file. Question sets did not change the progress format: they added a name beside the pointer, and a file written before them has none, which reads as a question belonging to no set — so it draws a new question and keeps every record.
- Natural deduction validates rule shape, accessible lines, and assumption discharge. Semantic equivalence never authorizes a proof step.
- `STATUS.md` owns local evidence. Linear project Stepwise owns execution: https://linear.app/acturea/project/stepwise-eda337d1c7f9 . Keep metrics out of Linear.
- One real instruction file: this file. `AGENTS.md` and `.github/copilot-instructions.md` are symlinks.
