# Stepwise

Offline Rust TUI and desktop window for Python evaluation, propositional truth evaluation, and classical natural deduction.

- Use tabs and explicit types. Keep the teaching rules separate from terminal rendering.
- `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked` are the native gates; at the root they build only `stepwise`, so the CLI never compiles a window library. The desktop adds `cargo fmt --all --check`, `bun run check`, `bun run lint` and `bun run build` in `desktop/ui`, then `cargo clippy --locked -p stepwise-desktop --all-targets -- -D warnings`, `cargo test --locked -p stepwise-desktop` and, since a release build embeds the built page, `cargo check --locked -p stepwise-desktop --features tauri/custom-protocol` after it.
- `.github/workflows/package.yml` is the only distribution pipeline, and it runs by hand: GitHub offers a `workflow_dispatch` run only once the file is on the default branch. Its first job calls `check.yml` through `workflow_call`, and every job that builds or archives the program needs it, so only a commit that passed the whole gate is packaged; `check.yml`'s concurrency group names the calling workflow, and the caller's group is its own, or the two deadlock. Packaging compiles with the day's stable, the channel the gate in the same run tests with: the project follows the latest release rather than pinning one. The runner images are named rather than `-latest`, so moving them is a commit of its own. The CLI ships as `stepwise-<version>-<target>` for `x86_64-unknown-linux-musl` (no INTERP header, no NEEDED entry), `aarch64-apple-darwin` and `x86_64-apple-darwin` (one architecture each, the Intel one cross-compiled on the arm64 runner) and `x86_64-pc-windows-msvc` (`+crt-static`, no C runtime import), as tar.gz or on Windows zip. Each holds LICENSE, README.md, THIRD-PARTY-NOTICES.txt and RUST-STD-COPYRIGHT.html, and every check reads the archive back rather than the file cargo wrote. Each job hashes the archive it checked, and SHA256SUMS is written from those hashes, so the downloaded bytes are held to the checked ones. THIRD-PARTY-NOTICES.txt is generated per target by cargo-about from `about.toml` and `about.hbs`, never written by hand; the Linux one also carries musl's licence, fetched by checksum for the musl version the toolchain links, so a Rust release that moves musl stops the run until that version and checksum move with it. The standard library's notices are the toolchain's own `COPYRIGHT-library.html`. A dependency under a licence `about.toml` does not accept fails the run until someone has read the licence and added it. A crate published without its licence file gets a checksummed `clarify` entry, because the SPDX text it would fall back to names no copyright holder; the run fails on that fallback rather than shipping it.
- The same manual `package.yml` builds desktop installers after the same gate, independently of the CLI notice/build jobs: separate arm64/x64 dmg on macos-26, NSIS/MSI on windows-2025, deb/rpm/AppImage on ubuntu-24.04. `tauri.package.conf.json` adds generated target-specific Rust, standard-library and page notices to the static LICENSE/COPYRIGHT/OFL resource mapping. Development cargo checks need no generated notices. The locked Vite build and `desktop/ui/licenses.ts` generate the page notices, including prebundled dependencies and font packaging; never replace missing copyright with generic SPDX text. `scripts/package/verify.py` extracts each installer, compares licence bytes, verifies the app signature/architecture in each dmg and measures the highest required GLIBC symbol across the Linux executable and AppImage ELF files. Only then does it hash the installer. The checksum job collects each complete successful family, so a broken desktop does not prevent CLI delivery or vice versa. `python3 -m unittest discover -s scripts/package -v` exercises these verification gates. No Release, tag or runtime acceptance follows from a packaging run.
- Run `cargo test --locked --test python_oracle -- --ignored --nocapture` when changing Python semantics, and `cargo test --locked --test terminal -- --ignored --nocapture` when changing the terminal adapter. Both are opted into because they need CPython and a pty; Python is a development oracle and a test driver, never a runtime dependency.
- Evidence is a test, not a committed transcript. Anything `STATUS.md` claims must point at something runnable.
- `src/core`: the language-neutral teaching machinery — stable tree IDs, substitution and source mapping, which steps are selectable, typed answer validation, feedback, history and replay. It reaches a language only through `Language` and the closed `Op` pair, and `src/core/language.rs` is the only file in core that names a language module — `rg 'crate::(python|logic)' src/core/` should report no other. Each language owns its own session constructor; no operator rule, precedence number or per-operator explanation lives in core. Core words only what it judged — an attempt, or the next step a hint names; those sentences are shared by both languages and never reworded per language. Two name Python because only Python raises: the note on a limit of this program and the note that an exception came from a sub-expression the student chose to compute. It words nothing about the practice around a step, so `Session::hint` returns `None` where no step is left instead of naming a key.
- `src/python`: Python parsing, operator rules, numeric and type semantics, precedence, short-circuit operand rules, every Python explanation, and the Python question grammar.
- `src/logic`: shared symbol aliases, propositional semantics and precedence, bounded BDD equivalence, scoped proof rules, and the propositional question grammar. A proof rule is documented twice, and `tests/proof_questions.rs` holds both to the rules it applies: each rule heads its own line of `RULES` (two may share one as `a / b`), and each sits in backticks in the first column of README's rule table. A rule added to the checker is added to that test's `applied` list too.
- `src/generate`: the shared seed protocol, sampling loop and suitability check; each language module owns its own grammar. Both reference routes — the short-circuit order and computing every operand — must complete generated questions with manageable answers; between them they bound every mix a student may take. Bump the generation ID version when changing the seed protocol; persisted random questions reconstruct from that ID. Default startup generates a random question or resumes unfinished progress; `n` generates the next question and `p` revisits the current run's history. Samples require `--exercise`.
- `src/exercises.rs`: the question model and the one file format behind it. A question set is a versioned TOML file — `version`, a stable set `name`, title, optional description, and an ordered list of questions that each name their own `kind`: an evaluation question gives source, language and bindings, a proof question gives premises and a conclusion formula. A question's `name` is its identity and the word typed after `--exercise`; it is author-written, so it is a name and not an `id`. The only fields nothing can check are `title` and the optional `note`, and `note` is optional for exactly that reason — a sentence is either true of the question or not, and only a reader can tell. The set compiled into the binary is that one load path's default value, not a second entry: `builtin()` hands `QuestionSet::parse` the embedded `questions/builtin.toml` exactly as a front end hands it a file it read, and `--exercise` resolves against whichever set is loaded. Reading a file belongs to the CLI or the window; the library takes text, checks it and gives back a set, so no path reaches `src/app`. Bindings stay strings of the owning language's source literals — `"0"`, `"0.0"`, `"-0.0"` and `"True"` keep their type and precision — and are never pre-converted to a TOML number or boolean. Every struct denies unknown fields, so a field belonging to the other question type is refused rather than ignored. Bump `FORMAT_VERSION` when the protocol changes; a file naming another version is refused, not guessed at, and a version-1 file is told the one change that upgrades it (version 2 dropped `evaluation`). No JSON question loader remains.
- `src/app`: the front-end-independent application layer — the course of questions and where the next one comes from, the current session with the student's selection, draft and feedback, undo, reset, the archived history, and the progress snapshot. It names no terminal or window library and no file path: `rg 'crossterm|ratatui|PathBuf|std::fs' src/app/` must report nothing. Progress arrives as an explicit snapshot and leaves through `progress()`; deciding when to write it belongs to whoever owns the terminal or the window. Wording runs the other way: a `Report` is a sentence the teaching rules already worded, a sentence a front end handed in through `note`, or a `Notice` — a closed reason with no sentence at all. `Notice` stands beside core's `FeedbackKind` and is never merged into it. Several reasons cannot be said without naming a key or an input device, and the rest keep the same rule rather than splitting the set: `rg 'Enter|Esc|F1|按 [a-z]|点击' src/app/ src/core/` must report nothing. An archived line is the exception and stays here, worded once for every front end — the transcript's taken-back marker and `ProofPractice::appended` are the permanent record, not a live notice. Every match over `Notice` spells its variants out rather than using a wildcard, so a new reason stops compiling until each place has decided what it means. `Course` carries the question-source strategy — random practice, or a fixed set walked in order — so a new source adds a variant rather than a second way to change question. An ordered set ends at its last question instead of generating one. A course holds questions of both kinds: `Lesson` moves through it — forward, back, the end of a set, recording — and the `Task` in hand is an evaluation `Practice` or a `ProofPractice`, so no front end keeps its own way to move between the two, and a set's proofs are never filtered out of its order. Where a course opens is chosen before it is built, by `resume_in_set` and `resume_or_generate`, and an unfinished proof is saved work there like any other. The transcript archives both kinds, so a proof's lines are archived by the same rule for every front end; each line is typed — `Archived::{Break, Heading, Bindings, Expression, TakenBack, ProofLine}` — so a terminal prints it and a window lays it out, with the words the same. `Practice::raised` sums up an evaluation that ended in an exception, worded here once like an archived line.
- `src/tui`: rendering and input only — an adapter that maps terminal events to app operations and draws app state. It keeps no second copy of the session or the progress, and re-derives no teaching rule: draft ranges, the node under a source byte and which display states to archive all come from `src/app`. It owns every word for every `Notice` — `src/tui/say.rs`, alongside the `?` help in `src/tui/keys.rs` — and its match over `Notice` is exhaustive, so a new reason stops compiling until this front end has said it. Which reports read as good news stays the app layer's rule; `say` asks rather than deciding again. One loop runs the whole lesson and draws whichever view the task in hand needs; in the proof view every letter is proof input, so changing question there takes Ctrl+N / Ctrl+P. Never preselect the correct next node in practice.
- `src/desktop`: the desktop window's Rust half — an adapter over `src/app` as `src/tui` is, for a page that draws and forwards input. A `Desk` maps each `Command` the page sends to an app operation and hands back a `View`: runs and extents from `node_owners` and `render_with_ranges`, blanks from `draft_spans`, the record above the line in hand from the `Transcript`, how a question ended from `Practice::raised`. It keeps no second copy of the session or the progress and re-derives no teaching rule; what it tracks is only what a window needs around the lesson — whether the student has pointed at a node, whether the last command reached the teaching rules (so a turned-down report is a mistake only after a submit or a selection, never after a hint, and a command that changes nothing leaves the last verdict standing), whether the rules are shown, and the `edition` of the board, which moves on whenever a command leaves a different blank, line or draft under the page's field. It owns this window's words for every `Notice` in `src/desktop/say.rs`, exhaustive like the terminal's. It takes a set's text and hands back a progress snapshot: `rg 'tauri|wry|tao|std::fs|PathBuf' src/desktop/` must report nothing, and it needs nothing beyond serde. Under `cargo test` its types write their TypeScript declarations to `desktop/ui/src/lib/protocol` (ts-rs, a dev-dependency); regenerate rather than edit them, and CI fails on drift.
- `desktop/`: the window around `src/desktop`. `desktop/src-tauri` is the Tauri 2 shell (workspace member `stepwise-desktop`): it reads question files and the progress file, writes progress whenever the desk says it changed — and on quitting only a change whose write had failed, so an idle window never overwrites what the terminal saved meanwhile — and takes `--progress-file` / `--no-save` like the CLI; the progress path and format are the terminal's, so either front end resumes the other's work. `desktop/ui` is the page (Svelte 5 + TypeScript, built with bun and Vite): it draws a `View` and forwards `Command`s, and never computes a byte offset, decides a step or words a teaching sentence — chrome labels are its own. The draft field holds the text while its blank is open and the desk mirrors it one command per edit, in order; a command that changes the blank, the line or the draft under the field moves the board to a new `edition`, the field takes the desk's value only when an edition mounts it, and the desk drops a draft sent for an earlier edition, so a late reply never overwrites fresher typing or an IME composition, a late keystroke never lands in the next blank, and one typed while a refusal or a hint was on its way still counts. While a blank or a proof line is open every typed character belongs to it, though a focused button keeps its own keys, and Enter is ignored while composing (`isComposing` or keyCode 229). Formula lines wrap only between tokens and keep short bracket groups on one line (`Grouped.svelte`); that is typesetting, not a rule. A skin fills the role tokens `src/styles/base.css` names — components name roles (the line in hand, the line being written, a mistake, what is pointed at, what was accepted), never colours. The built-in skins (blackboard, terminal, notebook, native) are one stylesheet each in `desktop/ui/src/skins`; a colour theme found in VS Code or a fork of it, or imported from a theme file, is turned into the same tokens by the shell. Appearance — the skin, editor themes, fonts — is a preference of the window and nothing else: it lives in `desktop/src-tauri/src/appearance`, is saved in `appearance.json` beside the default progress file — `--progress-file` and `--no-save` govern the student's work, not the window's look — and never reaches `src/desktop`, the `View` or the progress; the stepwise library gains no parser or font crate for it (`cargo tree -p stepwise -e normal` names no fontdb, jsonc-parser or ttf-parser). An editor theme is mapped role by role through candidate keys and VS Code's own defaults, and every role clears a contrast floor against the surface (ink 7:1, faded ink and marks 3:1) or is moved until it does; the shell's tests run every theme installed on the machine through those floors. Fonts are picked per role — follow the skin, follow the editor's `editor.fontFamily`, or an installed family, which is prepended to the skin's stack so Chinese and missing logic symbols still fall back. `bun run gallery` builds every screen from fixtures into one file for design review. The window is compact and resizable, with no tree panel and no second pane: a question list opens as a sheet over the board. Never preselect the correct next node here either.
- CLI requires exactly one of `--python` / `--logic`; proofs require `--logic`. `--set FILE` imports a question set and replaces the embedded one, turning practice into that file's order; it conflicts with a custom expression, a written-out proof (`--goal`/`--premise`), `--random` and `--equivalent`, and the required language selects inside the set. `--proof NAME` and `--exercise NAME` go through one lookup against whichever set is loaded — `--proof` only insists the question is a proof — so no proof name is hard-coded outside a question set, and `--check-proof` takes its proof from `--proof` or `--goal`. clap waives a missing `requires` when the missing argument conflicts with one already given, which silently drops the flag: an argument that requires another also carries that one's conflicts (`PROOF_ONLY`, `NOT_RANDOM`), and a new `requires` gets the same treatment. Help/version are exempt. Keep exercise headers to the language/name only; there is no short-circuit status to display.
- The terminal stays inline in the primary terminal buffer; no fullscreen, alternate screen, tree panel or Tab views. Keep the full expression visible above the inline draft and append accepted history to native scrollback.
- Selecting any variable occurrence permits substituting every occurrence of that name in one answer, regardless of precedence. Independent ready operations at equal precedence may be chosen in either order; parentheses have local precedence scopes, not a global depth ranking. Preserve grouping dependencies and operator association; a short circuit is never held back by work inside the operand it skips. This is a priority-based teaching exercise, not strict execution tracing. Clicking a group whose contents are a value removes exactly that pair immediately, without requesting an answer. Record the click as an undoable/replayable action with no input. Preserve syntactically necessary parentheses around a negative power base even after its grouping step.
- Automatically open the answer blank only when the whole expression is a binary operation over two known values. Never auto-submit or auto-solve. Explicit grouping and short-circuit selection remain student actions.
- Exception at completion: when the whole expression is a minus sign over an unsigned numeric value, finish with that signed value without another answer. Do not apply this to inner negations, remaining groups, bool conversion or double negatives. Undo restores the last student step; completion adds no recorded attempt.
- Generate steps, expected values and feedback from the parsed expression, bindings and evaluation rules. Exercises contain source and bindings, never a scripted solution; a proof question gives premises and a conclusion and no step of its derivation. A complete proof lives only in tests — checker fixtures under `tests/fixtures` and test code — never as a sample, in documentation or in anything the program shows: README and the in-app rules explain how to write a line instead, and their examples answer no question. Prose is optional and is never the source of a teaching step. Keep concrete grouping separate from the semantic formulas used by proof checking.
- No evaluation mode. In one session a student may short-circuit wherever the operands already decide it (Python `and`/`or`; logic `∧` `∨` `→`, never `↔`) or keep computing the operands it would skip, chosen per operation in every state, and may still short-circuit after computing part of an operand. `Session::allowed_steps` is that set. It is not the fixed short-circuit reference: `Session::next_step` picks the step a hint names and `--trace` prints, and random-question suitability walks `reference_step` along the short-circuit and the complete route — keep the allowed set and the reference distinct, and never use the reference to preselect. A refused selection names work the student may do now: inner work inside it, or the higher-precedence step beside it, never an ancestor that would remove it. Python mode stays a teaching exercise: computing a skipped operand is extra evaluation, not Python's order. An exception from extra evaluation ends the question and says it came from the chosen sub-expression; undo restores it. No mode, no `s` key, no `--evaluation`, no `evaluation` field, no status heading. Bump the teaching-rule string (`RULES` in `src/core/session.rs`) whenever the allowed set changes.
- Progress must be isolated by teaching-rule version, language, expression and typed valuation, never by the path a student took: one question keeps one record. Attempts stay keyed by that content, so an edited question starts fresh without losing the old record and a moved file changes nothing; the pointer to the question in hand additionally names its set, so two sets that both hold a question named `q1` never reopen each other's work. A set that fails to load must not touch the progress file. Question sets did not change the progress format: they added a name beside the pointer, and a file written before them has none, which reads as a question belonging to no set — so it draws a new question and keeps every record. Progress version 3 dropped `mode`: a file of version 1, or of the short-lived version 2 the first question-set commits wrote in the same shape, loads with `mode` dropped — read only as one of the two strategies such a build wrote — and every record and the pointer kept verbatim, never re-keyed; any other version is refused and the file left untouched.
- Natural deduction validates rule shape, accessible lines, and assumption discharge. Semantic equivalence never authorizes a proof step.
