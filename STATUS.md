## Implemented

- Expression TUI: click an operation in the current expression to replace its displayed span with `____`, then enter a typed literal or exception name. Operation selection never supplies an answer; wrong answers preserve the draft. Correct submissions contract the subtree and append the previous expression to the transcript when its displayed text changes. Independent ready computations at equal precedence may be chosen in either order within their scope; independent parentheses have local precedence scopes, not a global depth ranking. Group dependencies and operator association remain enforced, except that a short circuit is never held back by work inside the operand it skips. This is a priority-based teaching exercise, not strict Python execution tracing.
- Inline terminal interaction: uses the primary terminal buffer and a five-row active area, with accepted expressions appended to native scrollback. No fullscreen, alternate screen, tree panel or Tab switching. Clicking keeps the unmasked expression above the draft. Startup shell output and accepted history survive redraws and normal exit; undo/reset append a marker. Long current content and feedback scroll in place. Natural deduction uses the same terminal lifecycle.
- Explicit groups are independent teaching actions in both expression languages: `2 + (3*4)` → `2 + (12)` → `2 + 12` → `14`. Once the contents are a value, clicking the group removes exactly one pair without requesting an answer. The click is saved with no input, and supports undo/replay. Unfinished groups cannot be removed. Display preserves source aliases, grouping and spacing, adding necessary separation around word operators and protection around negative power bases.
- Python variables support typed literal assignments. Any variable occurrence can be selected regardless of precedence; every occurrence of that name becomes a blank and one correct answer replaces them all. Propositions behave the same way. Undo/replay treats the batch as one student action. Given values may be substituted into guarded branches without executing their operations. The embedded long formulas cover arithmetic, unary signs, right-associative powers, comparisons, boolean operators and all five propositional connectives. Intermediate states, answers and feedback come from the source, bindings and rules; exercises contain no scripted solutions.
- A whole binary expression over two known values automatically opens a blank, keeping the full expression above it. It never computes or submits on the student's behalf. Groups and unread variables do not trigger this shortcut. Resume, undo and reset apply the same condition.
- A final minus sign over an unsigned numeric value directly becomes the completed value without another answer. For `-2 ** 2`, submitting `4` for the power finishes at `-4`. Inner negations, remaining groups, double negatives and bool-to-number conversion remain separate steps. Completion creates no synthetic student attempt; undo returns to the last submitted step.
- Python and propositional logic are separate language modules. `src/python` owns Python parsing, operator rules, numeric and type semantics, precedence, short-circuit operand rules, explanations and question grammar; `src/logic` owns the propositional equivalents plus natural deduction; `src/core` keeps only the shared teaching tree, node identity, substitution and source mapping, step selection, typed feedback, history and replay, reaching a language through the `Language` and `Op` types alone; each language builds its own session, so `src/core/language.rs` is the single file in core that names a language module. `src/generate.rs` keeps the seed protocol, sampling loop and suitability check. Behaviour, feedback text, seed IDs and progress keys are unchanged.
- A front-end-independent application layer sits between the teaching rules and the terminal. `src/app` owns the course of questions and where the next one comes from, the current session with the student's selection, draft and feedback, undo, reset, the archived history and the progress snapshot; it names no terminal library, window toolkit or file path, and progress arrives as an explicit snapshot that the caller writes out. `src/tui` is an adapter: it maps Crossterm events to app operations and draws app state, keeping only hit boxes, scrolling, the cursor, its own key help and the run lifecycle. Draft ranges, the node under a source byte and which display states to archive now come from the app layer instead of the renderer. Natural deduction restores, submits, undoes and records through the same layer. `Course` carries the question source — random practice, or a fixed set walked in order — so generating the next random question is not the only way to change question. Behaviour, feedback text, seed IDs and progress keys are unchanged.
- One course carries both kinds of question. `Course` holds `Question`s; `Lesson` moves through it — next, previous, the end of an ordered set, recording — and the `Task` in hand is an evaluation `Practice` or a `ProofPractice`, so neither the terminal nor a later window keeps a second way to move between an expression and a proof. Nothing is carried across a proof: an evaluation question opens on its own record whichever way the course reached it. A proof question records the progress pointer like an evaluation question does, leaving the evaluation records alone, so resuming — a bare launch in random practice, or an ordered set's search for its first unfinished question — treats an unfinished proof as saved work and a proof whose conclusion stands outside every assumption as finished. The transcript archives both kinds by one rule: a proof's header and premises when its block opens, each accepted line once, the taken-back marker on undo, and a blank line between blocks. The terminal runs the whole lesson in one loop and draws whichever view the task needs; the proof view changes question with Ctrl+N / Ctrl+P because every letter there is proof input.
- Teaching notices are typed reasons, not sentences. `Practice` and `ProofPractice` report a `Report`: either a sentence the teaching rules already worded, or one of nine closed `Notice` reasons — question opened, draft open, final pair opened on its own, no step left to hint at, step taken back, question restarted, ordered set ended, proof opened, proof line taken back. There were ten until P-741 retired the strategy switch. Saying any of them means naming a key or an input device, so `src/tui/say.rs` owns the words next to the `?` help in `src/tui/keys.rs`, and its match over `Notice` is exhaustive. `Session::hint` returns `None` where no step is left rather than naming `n` and `u`, so core still words only what it judged. A second front end answers the same reasons instead of copying this one's wording. The terminal shows the same sentences it always did.
- Questions come from a versioned TOML question set that a teacher can edit, distribute and import. A set names a format version, a stable set `name`, a title, an optional description and an ordered question list; each question writes its own `kind` out rather than being inferred from which fields it happens to carry. A question's `name` is its identity and the word typed after `--exercise` — author-written, so a name and not an ID. An evaluation question gives source, language and bindings; a proof question gives premises and a conclusion formula. The only unverifiable fields are `title` and the optional `note`; nothing requires a note, because a question with none is complete — every step, value and explanation comes from the rules applied to the source. Every struct refuses unknown fields, so a field belonging to the other kind — `expression` on a proof, `premises` on an evaluation question — is refused instead of ignored, and since version 2 so is `evaluation` on either kind. Bindings stay strings of the owning language's source literals, parsed by that language: `"0"`, `"0.0"`, `"-0.0"` and `"True"` keep their type and precision, which a TOML number or boolean would flatten. A set holds question text, conditions and metadata and never a worked solution.
- One load path, with the embedded set as its default value. `exercises::builtin()` hands `QuestionSet::parse` the embedded `questions/builtin.toml`; `--set FILE` hands it a file the CLI read, through `QuestionSet::import`, which adds the single rule only a file has to answer — it may not call itself `builtin`, the name progress keeps the embedded questions under. `assets/exercises.json` and its loader are gone; no JSON compatibility reader remains. `--exercise` resolves against whichever set is loaded, and a `kind = "proof"` question opens the natural-deduction practice the same rules already check. The library takes text and returns a checked set, so no file path reaches `src/app`.
- The built-in proofs are data. `mp`, `raa` and `identity` are `kind = "proof"` questions of `questions/builtin.toml` with their premises and conclusion carried over character for character, and `proof_for`'s hard-coded `match` and `--proof`'s three-name whitelist are gone. `--proof NAME` and `--exercise NAME` go through one lookup against the loaded set — `--proof` additionally insists on a proof — so `--logic --list` lists the built-in proofs with their sequents and `--logic --exercise raa` opens reductio directly. `--goal` with repeatable `--premise` writes out a proof belonging to no set and needs no `--proof` beside it. `--check-proof FILE` is unchanged as the checker entry and takes its proof from `--proof` or `--goal`. A complete proof lives only in tests — checker fixtures under `tests/fixtures` and test code; README and the in-app rules (`F1`) document how to write a line instead of showing a worked solution, and their examples answer no question.
- `--set` makes the file the course: its questions of the required language, evaluation and proof alike, in file order, ending at the last one with the course-ended reason instead of generating. A launch opens the first question still unfinished, looked for from wherever progress left off inside that set; only one pointer is saved, so a set returned to after working elsewhere is searched rather than restarted. Without `--set` nothing changed: a bare launch still resumes or draws a random question and `n` still generates. `--set` refuses every other question source — a custom expression, `--random`, `--seed`, `--goal`, `--premise`, `--equivalent` — rather than accepting and dropping it; `--proof NAME` names a question of the loaded set like `--exercise` does, so it and `--check-proof` combine with `--set`, and `--assign` landing on a proof question is refused for the same reason.
- A set is checked before practice starts, and the whole file is refused with the question and field to correct. TOML itself reports syntax, wrong field types, unknown fields and unknown question kinds with a line and a column; this program then reports a version other than 2 — read on its own before the rest, so a set from another protocol names the version rather than the field a reader tripped over first, and a version-1 set is told the one change that upgrades it — an empty or duplicate question name, an empty set name or title, a set with no questions, a binding that is not a literal of its language, and an expression, premise or conclusion that does not parse. Limits: 1 MiB per file, 1024 questions, 64 premises. A question that ends in an exception is legal teaching material and loads.
- Progress names the set as well as the question. Attempts stay keyed by content — teaching-rule version, language, bindings, source — so an edited question starts fresh with its old record intact and a moved or renamed file changes nothing; the pointer additionally names the set, so two sets that both hold a question named `q1` never reopen each other's work. A set that fails to load exits before the progress path is resolved, so a bad file cannot touch saved work. Question sets did not change the progress format: they added a name beside the pointer, and a file written before them has none, which reads as a question belonging to no set. Such a file loads, every record is kept, and the stale pointer draws a new question instead of reopening one; a record written under the current teaching rules still replays under its own question.
- Short circuit or continue, with no mode (P-741). Wherever the operands already decide a Python `and`/`or` or a propositional `∧`, `∨` or `→`, one session lets the student take the short circuit or keep computing the operands it would skip, chosen afresh per operation in every state, so part of an operand may be computed and the short circuit still taken afterwards; `↔` never short-circuits. `Session::allowed_steps` is that set: a step is allowed when some choice of short circuit or continue at each such operation allows it, precedence holds inside each bracket scope, and a short circuit is never held back by work inside the operand it skips. Bindings and finished brackets stay independent actions everywhere. `Session::next_step` stays the fixed short-circuit reference — the step a hint names and `--trace` prints — and is always one of the allowed steps; nothing uses it to preselect. Random-question suitability walks the crate-private `reference_step` along the short-circuit and the complete route instead, as the base commit's free `next_step` did. Nothing is rejected as skipped any more: a selection is refused as finished, gone, already a value, not yet decided or out of order, and the last two name work the student may do now wherever there is some — an allowed step inside the selection, or the nearest allowed higher-precedence operation in its bracket scope — never an ancestor whose step would remove the selection; the out-of-order sentence no longer mentions short circuit. A Python `and`/`or` returns the deciding operand with its own type. While part of the skipped side is unreduced the explanation still says it is skipped; once every later operand is a value it says instead that they do not affect the result and that Python would not compute them. A `ZeroDivisionError` explains the operation — the divisor is zero and this step raises — rather than claiming where Python stops. An exception still ends the question. Where the reference route, run on from the state the student reached, raises at that very node the sentence is unchanged; where it would not — it short-circuits past that node or raises elsewhere first — the correct answer adds that the exception came from the sub-expression the student chose and that Python running the source would not raise it there, keeping only the first half when a limit of this program stops the reference route before it either raises there or discards that node. The terminal's completion line and the line left on quitting name the sub-expression that raised (`完成：3 / 0 引发 ZeroDivisionError`) rather than pairing the source with a bare exception name, also after reopening from the record, and its `?` help says that continuing is extra evaluation, not Python's order. Undo restores the question, and a short circuit then finishes normally. The progress key names the teaching rules (`flexible-substitution-v4`), language, bindings and source and no strategy, so one question keeps one record whichever path the student takes. `EvaluationMode` left the public API along with `Session::mode`, `Practice::toggle_mode`, `Notice::ModeSwitched`, `FeedbackKind::Skipped`, `app::starting_mode`, the terminal's `s` key and `--evaluation`, which clap now refuses as an unexpected argument. Python mode stays a teaching exercise: computing a skipped operand is extra evaluation, not Python's order.
- Progress files moved to version 3 and question sets to version 2 with that change. A progress file no longer saves `mode`. A version-1 file still loads, and so does a version-2 one — the first question-set commits wrote 2 in the same shape for a short while before setting it back to 1: `mode` is dropped, every record is kept verbatim — its evaluation records under their old `flexible-substitution-v3` keys, inert rather than re-keyed or merged — and the pointer is kept. An evaluation question in hand then has no record under the current rules: a random question, or the question an ordered set resumes at, reopens from its start, while a bare launch whose pointer names a set question draws a new random question, since nothing under the current rules says it was begun; a proof resumes where it was; the next save writes version 3. Any other version is refused with the localized reason and the file untouched. A question set dropped the evaluation question's `evaluation` field: a version-1 set is refused on its version with the one change that upgrades it, and `evaluation` in a version-2 file is an unknown field on either kind. The embedded and example sets are version 2, and the example's `eager-division` became `guarded-division` over the same expression and bindings.
- Propositional evaluation of negation, conjunction, inclusive disjunction, material implication, and equivalence, with supplied valuations. ASCII, Unicode, and word aliases share a parser; no formula simplification occurs before the student attempts a step.
- `boolean_expression` BDD equivalence check independent from the teaching tree. This establishes semantic equivalence, not a valid natural-deduction step.
- Classical propositional natural-deduction TUI: named introduction/elimination rules, modus ponens, contradiction, reductio, nested assumptions, accessible-line checking, and discharge. Closed subproof lines cannot be cited; reaching the goal inside an open assumption is not completion.
- Embedded exercises, custom expressions/valuations/proof premises and goals, trace and proof-file CLI modes, atomic progress storage with replay, keyboard/mouse selection, narrow-terminal handling.
- CLI requires exactly one of `--python` or `--logic`, including list/trace modes; natural deduction is part of `--logic`. Missing or conflicting language flags fail before starting a terminal or loading progress. Help/version do not require a language. Choosing a language still defaults to random questions.
- Default startup generates a random question, or resumes unfinished progress. Completed questions give way to a new random question on the next launch. Samples remain available through `--exercise`. `n` generates further questions; `p` revisits questions from this run. `--random` forces a new question, `--seed` reproduces one. A versioned seed in the exercise ID reconstructs the current random formula and bindings on restart. Generation uses bounded arithmetic/comparison/boolean or propositional grammars and verifies manageable, exception-free completion on both reference routes — the short-circuit order and computing every operand — which bound every mix a student may choose; solution steps are never stored in a question.
- Desktop window (P-652): a compact, resizable Tauri 2 window over the same app layer. `src/desktop` is its Rust half — a `Desk` maps each command the page sends to a `Lesson` operation and hands back a `View`; the page (`desktop/ui`, Svelte 5 + TypeScript) draws it and forwards input, and computes no byte offset, decides no step and words no teaching sentence. Clicking a sub-expression writes the next line beneath it with that node blanked; the blank takes the typed answer, one answer fills every occurrence of a name, a wrong answer keeps the draft, and the line in hand shows which node the blank came from. Bracket removal, the final pair, the final negative value, exception endings, undo, restart, hints, the question list of the loaded set, random practice, opening a TOML set from a file dialog, ordered sets to their end, and natural-deduction proofs in Fitch layout all go through the same app-layer calls as the terminal. The desktop shares the terminal's progress file and format, so either front end resumes the other's work.
- Two skins, one stylesheet each, over components that name roles rather than colours: a blackboard (LXGW WenKai and its Mono cut, roughjs chalk marks) and a terminal skin (Menlo and the terminal version's colours). The skin is a per-viewer preference kept by the page.
- The transcript's lines are typed (`Archived`), and `Practice::raised` sums up an exception ending once for both front ends; the terminal prints exactly what it printed before.

- No student usability study or classroom acceptance has been performed.

## Deliberate first-version limits

A question set's ID is a global name: two files that declare the same ID are one set as far as progress is concerned, which is what lets a file move without losing work. Only `builtin` is reserved. One pointer is saved, so alternating between sets does not remember a position in each; returning to a set finds its first unfinished question instead. A set's `description` is part of the format and is not shown by the terminal front end. An evaluation question that ended in an exception counts as finished, so a relaunch moves past it; taking the exception back is an undo in the same run, or after `p` returns to it. Evaluation work saved under earlier teaching rules, including every version-1 record, stays in the progress file but does not replay. Python is a bounded expression subset; variables require supplied literal bindings. No strings, calls, assignment statements, containers, chained comparisons, complex values or nonfinite floats. Group removal is an explicit teaching action. Syntactically necessary brackets around a negative power base remain visible after that group is processed, without creating another action. Logical languages are propositional, not first-order or modal. Natural deduction has a basic rule subset and no disjunction elimination or proof search. Proof entry is currently a structured text line. One progress file is intended for one running instance. See README for exact supported syntax and size limits.
