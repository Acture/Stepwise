## Implemented

- Expression TUI: click an operation in the current expression to replace its displayed span with `____`, then enter a typed literal or exception name. Operation selection never supplies an answer; wrong answers preserve the draft. Correct submissions contract the subtree and append the previous expression to the transcript when its displayed text changes. Independent ready computations at equal precedence may be chosen in either order within their scope; independent parentheses have local precedence scopes, not a global depth ranking. Group dependencies, operator association and short-circuit guards remain enforced. This is a priority-based teaching exercise, not strict Python execution tracing.
- Inline terminal interaction: uses the primary terminal buffer and a five-row active area, with accepted expressions appended to native scrollback. No fullscreen, alternate screen, tree panel or Tab switching. Clicking keeps the unmasked expression above the draft. Startup shell output and accepted history survive redraws and normal exit; undo/reset append a marker. Long current content and feedback scroll in place. Natural deduction uses the same terminal lifecycle.
- Explicit groups are independent teaching actions in both expression languages: `2 + (3*4)` → `2 + (12)` → `2 + 12` → `14`. Once the contents are a value, clicking the group removes exactly one pair without requesting an answer. The click is saved with no input, and supports undo/replay. Unfinished or skipped groups cannot be removed. Display preserves source aliases, grouping and spacing, adding necessary separation around word operators and protection around negative power bases.
- Python variables support typed literal assignments. Any variable occurrence can be selected regardless of precedence; every occurrence of that name becomes a blank and one correct answer replaces them all. Propositions behave the same way. Undo/replay treats the batch as one student action. Given values may be substituted into guarded branches without executing their operations. The embedded long formulas cover arithmetic, unary signs, right-associative powers, comparisons, boolean operators and all five propositional connectives. Intermediate states, answers and feedback come from the source, bindings and rules; exercises contain no scripted solutions.
- A whole binary expression over two known values automatically opens a blank, keeping the full expression above it. It never computes or submits on the student's behalf. Groups and unread variables do not trigger this shortcut. Resume, undo and reset apply the same condition.
- A final minus sign over an unsigned numeric value directly becomes the completed value without another answer. For `-2 ** 2`, submitting `4` for the power finishes at `-4`. Inner negations, remaining groups, double negatives and bool-to-number conversion remain separate steps. Completion creates no synthetic student attempt; undo returns to the last submitted step.
- Python and propositional logic are separate language modules. `src/python` owns Python parsing, operator rules, numeric and type semantics, precedence, short-circuit operand rules, explanations and question grammar; `src/logic` owns the propositional equivalents plus natural deduction; `src/core` keeps only the shared teaching tree, node identity, substitution and source mapping, step selection, typed feedback, history and replay, reaching a language through the `Language` and `Op` types alone; each language builds its own session, so `src/core/language.rs` is the single file in core that names a language module. `src/generate.rs` keeps the seed protocol, sampling loop and suitability check. Behaviour, feedback text, seed IDs and progress keys are unchanged.
- A front-end-independent application layer sits between the teaching rules and the terminal. `src/app` owns the course of questions and where the next one comes from, the current session with the student's selection, draft and feedback, undo, reset, strategy switching, the archived history and the progress snapshot; it names no terminal library, window toolkit or file path, and progress arrives as an explicit snapshot that the caller writes out. `src/tui` is an adapter: it maps Crossterm events to app operations and draws app state, keeping only hit boxes, scrolling, the cursor, its own key help and the run lifecycle. Draft ranges, the node under a source byte and which display states to archive now come from the app layer instead of the renderer. Natural deduction restores, submits, undoes and records through the same layer. `Course` carries the question source — random practice, or a fixed set walked in order — so generating the next random question is not the only way to change question. Behaviour, feedback text, seed IDs and progress keys are unchanged.
- Teaching notices are typed reasons, not sentences. `Practice` and `ProofPractice` report a `Report`: either a sentence the teaching rules already worded, or one of ten closed `Notice` reasons — question opened, draft open, final pair opened on its own, no step left to hint at, step taken back, question restarted, strategy switched, ordered set ended, proof opened, proof line taken back. Saying any of them means naming a key or an input device, so `src/tui/say.rs` owns the words next to the `?` help in `src/tui/keys.rs`, and its match over `Notice` is exhaustive. `Session::hint` returns `None` where no step is left rather than naming `n` and `u`, so core still words only what it judged. A second front end answers the same reasons instead of copying this one's wording. The terminal shows the same sentences it always did.
- Questions come from a versioned TOML question set that a teacher can edit, distribute and import. A set names a format version, a stable set ID, a title, an optional description and an ordered question list; each question writes its own `kind` out rather than being inferred from which fields it happens to carry. An evaluation question gives source, language, bindings and an optional opening strategy; a proof question gives premises and a conclusion formula, separate from the prose `goal` both share. Every struct refuses unknown fields, so a field belonging to the other kind — `evaluation` on a proof, `premises` on an evaluation question — is refused instead of ignored. Bindings stay strings of the owning language's source literals, parsed by that language: `"0"`, `"0.0"`, `"-0.0"` and `"True"` keep their type and precision, which a TOML number or boolean would flatten. A set holds question text, conditions and metadata and never a worked solution.
- One load path, with the embedded set as its default value. `exercises::builtin()` hands `QuestionSet::parse` the embedded `assets/exercises.toml`; `--set FILE` hands it a file the CLI read, through `QuestionSet::import`, which adds the single rule only a file has to answer — it may not call itself `builtin`, the name progress keeps the embedded questions under. `assets/exercises.json` and its loader are gone; no JSON compatibility reader remains. `--exercise` resolves against whichever set is loaded, and a `kind = "proof"` question opens the natural-deduction practice the same rules already check. The library takes text and returns a checked set, so no file path reaches `src/app`.
- `--set` makes the file the course: its questions of the required language, in file order, ending at the last one with the course-ended reason instead of generating. A launch opens the first question still unfinished, looked for from wherever progress left off inside that set; only one pointer is saved, so a set returned to after working elsewhere is searched rather than restarted. Without `--set` nothing changed: a bare launch still resumes or draws a random question and `n` still generates. `--set` refuses every other question source — a custom expression, `--random`, `--seed`, `--proof`, `--goal`, `--premise`, `--check-proof`, `--equivalent` — rather than accepting and dropping it, and a proof question opened by `--exercise` refuses `--assign` and `--evaluation` for the same reason.
- A set is checked before practice starts, and the whole file is refused with the question and field to correct. TOML itself reports syntax, wrong field types, unknown fields and unknown question kinds with a line and a column; this program then reports a version other than 1 — read on its own before the rest, so a set from a later protocol names the version rather than the new field a reader tripped over first — an empty or duplicate question ID, an empty set ID or title, a set with no questions, a binding that is not a literal of its language, and an expression, premise or conclusion that does not parse. Limits: 1 MiB per file, 1024 questions, 64 premises. A question that ends in an exception is legal teaching material and loads.
- Progress names the set as well as the question. Attempts stay keyed by content — teaching-rule version, strategy, language, bindings, source — so an edited question starts fresh with its old record intact and a moved or renamed file changes nothing; the pointer additionally names the set, so two sets that both hold a `q1` never reopen each other's work. A set that fails to load exits before the progress path is resolved, so a bad file cannot touch saved work. The progress file is version 2: a version 1 pointer named a question without naming its set, and is refused with the file left untouched.
- Optional short circuit, switchable with `s` or `--evaluation`. Python defaults to short circuit; propositional logic defaults to eager evaluation. Headers show only the language/exercise name; switching reports the status in feedback. Help and operation feedback explain eager Python's teaching behavior. Neither variant silently skips an exceptional operand when eager.
- Propositional evaluation of negation, conjunction, inclusive disjunction, material implication, and equivalence, with supplied valuations. ASCII, Unicode, and word aliases share a parser; no formula simplification occurs before the student attempts a step.
- `boolean_expression` BDD equivalence check independent from the teaching tree. This establishes semantic equivalence, not a valid natural-deduction step.
- Classical propositional natural-deduction TUI: named introduction/elimination rules, modus ponens, contradiction, reductio, nested assumptions, accessible-line checking, and discharge. Closed subproof lines cannot be cited; reaching the goal inside an open assumption is not completion.
- Embedded exercises, custom expressions/valuations/proof premises and goals, trace and proof-file CLI modes, atomic progress storage with replay, keyboard/mouse selection, narrow-terminal handling.
- CLI requires exactly one of `--python` or `--logic`, including list/trace modes; natural deduction uses `--logic --proof`. Missing or conflicting language flags fail before starting a terminal or loading progress. Help/version do not require a language. Choosing a language still defaults to random questions.
- Default startup generates a random question, or resumes unfinished progress. Completed questions give way to a new random question on the next launch. Samples remain available through `--exercise`. `n` generates further questions; `p` revisits questions from this run. `--random` forces a new question, `--seed` reproduces one. A versioned seed in the exercise ID reconstructs the current random formula and bindings on restart. Generation uses bounded arithmetic/comparison/boolean or propositional grammars and verifies manageable, exception-free completion in both strategies; solution steps are never stored in a question.

## Deliberate first-version limits

A question set's ID is a global name: two files that declare the same ID are one set as far as progress is concerned, which is what lets a file move without losing work. Only `builtin` is reserved. One pointer is saved, so alternating between sets does not remember a position in each; returning to a set finds its first unfinished question instead. A set's `description` is part of the format and is not shown by the terminal front end. Built-in proof questions still come from `--proof` rather than the embedded set, and an ordered course walks evaluation questions only — [P-693](https://linear.app/acturea/issue/P-693) owns making the built-in proofs data and merging the two selection entries. Python is a bounded expression subset; variables require supplied literal bindings. No strings, calls, assignment statements, containers, chained comparisons, complex values or nonfinite floats. Group removal is an explicit teaching action. Syntactically necessary brackets around a negative power base remain visible after that group is processed, without creating another action. Logical languages are propositional, not first-order or modal. Natural deduction has a basic rule subset and no disjunction elimination or proof search. Proof entry is currently a structured text line. One progress file is intended for one running instance. See README for exact supported syntax and size limits.
